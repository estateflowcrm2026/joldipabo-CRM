# EstateFlow CRM — Offline Queue Contract

Date: 2026-09-19

This document is the API the offline action queue exposes to the rest of the app and the API the future sync worker must honour. The contract is referenced by [docs/PWA_OFFLINE_PLAN.md](PWA_OFFLINE_PLAN.md); the implementation lives at [src/services/offlineQueue.js](../src/services/offlineQueue.js).

The queue is a thin `localStorage`-backed log of pending mutations. It has no concept of a server — it only knows "I have an action, here is its payload." When a backend exists, a sync worker reads items out of this queue, applies them via the API repository, and updates the queue status.

---

## 1. Storage shape

One key, one JSON-encoded list. The key is `estateflow:offline-queue:v1` — the version suffix lets us invalidate the queue if the schema breaks without losing real data.

```text
localStorage["estateflow:offline-queue:v1"] = JSON.stringify([ ...items ])
```

Reading the queue is a single `JSON.parse`. No IndexedDB is required for the queue itself; binary photo data is referenced by key and stored separately (see §6).

The queue tolerates `QuotaExceededError`, `SecurityError` (private-mode browsers), and corrupt-JSON failures by falling back to an in-memory log with a console warning. The UI never crashes because of the queue.

---

## 2. Item shape

Every item, regardless of `type`, has the same envelope:

```ts
{
  id:         string;             // ULID-ish, generated by queueAction()
  type:       QueuedActionType;   // see §3
  payload:    object;             // see §4 per type
  status:     'pending' | 'syncing' | 'synced' | 'failed';
  createdAt:  string;             // ISO timestamp, set at queueAction()
  updatedAt:  string;             // ISO timestamp, updated on every state transition
  attempts:   number;             // count of sync attempts; defaults 0
  error?:     {                   // present when status === 'failed'
    code:     string;             // e.g. 'network', 'unauthorized', 'conflict'
    message:  string;             // human-readable for logs
    detail?:  object;             // free-form, e.g. server's 409 body
  };
  metadata?:  {                   // reserved for future sync/audit fields
    clientTimestamp?: string;     // device-side clock time of action
    networkType?:    string;      // last-known connection type
    appVersion?:     string;
  };
}
```

Only `id`, `type`, `payload`, `status`, `createdAt`, `updatedAt`, and `attempts` are written by `queueAction`. The rest are written by the sync worker.

---

## 3. Action types

```ts
type QueuedActionType =
  | 'attendance.checkIn'
  | 'attendance.checkOut'
  | 'visit.update'
  | 'photo.upload'
  | 'message.send'
  | 'listing.capture';
```

These are the only types the contract defines today. Adding a new type is a contract change — update this document, add the payload shape to §4, and bump the storage key version suffix (`v1` → `v2`).

### The allow-list invariant

`queueAction()` rejects any type not in the internal `ALLOWED_TYPES` set ([src/services/offlineQueue.js](../src/services/offlineQueue.js)) **by throwing, before the item is ever persisted**. The sync worker registers its handler types independently ([src/services/syncWorker.js](../src/services/syncWorker.js) `getSyncHandlers()`).

When those two lists drift apart, user actions are silently lost: the enqueue throws, nothing reaches storage, and the field staff member believes the capture was saved.

This is not hypothetical. `listing.capture` had a queueing helper (`offlineActions.js#queueListingCapture`), a sync handler, and a documented type — but was missing from `ALLOWED_TYPES` until 2026-09-24. **Every offline listing capture was dropped for the entire life of the feature.**

`src/services/offlineQueue.test.mjs` now asserts the invariant both ways:

- every type the sync worker registers is accepted by `queueAction`
- every type documented in §3 is accepted
- an unknown type throws an error whose message names the type, rather than vanishing

Run it with `npm test` (root) or `node src/services/offlineQueue.test.mjs`. When you add a queue type, that test fails until both lists are updated.

## 4. Payloads

### 4.1 `attendance.checkIn`

```jsonc
{
  "staffId":   "u-field-1",                     // required
  "siteId":    "proj-orchid" | null,           // optional
  "location": {
    "lat":      12.97,
    "lng":      77.59,
    "accuracy": 12,                            // meters
    "label":    "Live GPS capture"             // human-readable tag
  },
  "clientTimestamp": "2026-09-19T08:00:00.000Z"  // device clock
}
```

Server endpoint: `POST /api/v1/attendance/check-in` (defined in [docs/BACKEND_INTEGRATION_PLAN.md](BACKEND_INTEGRATION_PLAN.md#attendance)).

### 4.2 `attendance.checkOut`

```jsonc
{
  "staffId":   "u-field-1",
  "siteId":    "proj-orchid" | null,
  "location":  { /* same shape as checkIn.location */ },
  "clientHoursWorked": 8.5,                    // client estimate; server is authoritative
  "clientTimestamp":   "2026-09-19T17:00:00.000Z"
}
```

Server endpoint: `POST /api/v1/attendance/check-out`.

### 4.3 `visit.update`

```jsonc
{
  "visitId":  "vis-1",                         // existing record id (the demo seeded visits)
  "patch": {
    "status":    "Completed",
    "rating":    5,
    "feedback":  "Met lead on site, follow-up on Saturday",
    "completedAt": "2026-09-19T11:00:00.000Z"
  }
}
```

Only the patch fields need to be sent; the rest of the visit is unchanged. Server endpoint: `PATCH /api/v1/visits/:id`.

### 4.4 `photo.upload`

```jsonc
{
  "blobKey":  "photo-01HX...",                 // key into IndexedDB; see §6
  "metadata": {
    "projectId": "proj-orchid",
    "category":  "Progress",                   // matches photo category enum
    "caption":   "Site progress day 12",
    "geo":       { "lat": 12.97, "lng": 77.59 },
    "capturedAt": "2026-09-19T08:00:00.000Z"
  }
}
```

Server endpoints:
1. `POST /api/v1/photos:presign` → returns `{ url, fields, objectKey }`.
2. The worker uploads the Blob to `url` directly.
3. `POST /api/v1/photos` with `{ objectKey, ...metadata }` → creates the row.

### 4.5 `message.send`

```jsonc
{
  "threadId":  "thr-1",
  "fromId":    "u-field-1",
  "body":      "On site, customer wants Sunday visit",
  "channel":   "in-app"                        // | 'email' | 'sms' | 'whatsapp'
}
```

Server endpoint: `POST /api/v1/threads/:id/messages`.

### 4.6 `listing.capture`

Field-executive "Add collected property" flow when offline. Captures a
minimal property record on behalf of an owner; the sync worker expands it
into a full Listing record on the server side.

```jsonc
{
  "ownerName":       "Meera Iyer",                 // required
  "ownerPhone":      "+91 98456 11001",            // required (E.164-ish)
  "locality":        "Whitefield",                 // optional
  "serviceCategory": "rent",                       // rent | pg | land | office | resale | owner-listed
  "askingPrice":     45000,                        // optional, in INR (rent/month for rent/pg)
  "notes":           "3rd floor, east-facing",     // optional free text
  "userId":          "u-fe-arjun"                  // required — set by queueListingCapture
}
```

Server endpoint (future apiRepository-backed worker):
`POST /api/v1/listings` with the DTO shape described in
[docs/LISTINGS_MODULE.md](LISTINGS_MODULE.md).

## 5. Public API

The queue is exposed at [src/services/offlineQueue.js](../src/services/offlineQueue.js).

### `queueAction(type, payload, options?) → Promise<string>`

Enqueue an action. Returns the assigned `id`. `options` accepts:

- `metadata` — optional sync metadata merged into the item.
- `idempotencyKey` — if set, `queueAction` returns the existing id rather than creating a duplicate when an item with the same key (and `type`) is already pending. Useful for retry paths in the UI.

### `listQueuedActions({ status?, type? }?) → Array<Item>`

Read-only snapshot. Always returns a fresh array; never mutate the returned items directly.

### `markActionSynced(id) → void`

Mark an item synced. Idempotent.

### `markActionFailed(id, error) → void`

Mark an item failed. Increments `attempts`. `error` is shaped `{ code, message, detail? }`.

### `clearSyncedActions() → number`

Remove all `status === 'synced'` items. Returns the count cleared. Run after the sync worker has confirmed the actions are no longer needed locally.

### `resetQueue() → void`

Drop everything. Used by tests and by an explicit "Clear local data" admin action.

## 6. Photo Blob storage

Photos are large; the queue item carries only the IndexedDB key. A tiny helper at [src/services/photoStore.js](../src/services/photoStore.js) (added in the next phase) will provide:

- `putPhotoBlob(id, blob)` → stores under `${id}` in object store `photos`.
- `getPhotoBlob(id)` → returns the Blob (or null).
- `deletePhotoBlob(id)` → cleanup after a successful upload.

Until that helper is added, photo queues fall back to `data:` URLs in the payload (works for tiny demo images only).

## 7. Future sync worker contract

The worker, when it exists, lives at [src/services/syncWorker.js](../src/services/syncWorker.js) (future). It will:

1. Subscribe to `online`, `visibilitychange`, and the service worker `sync` event.
2. On trigger, call `listQueuedActions({ status: 'pending' })`.
3. For each item in createdAt order, call `markActionSyncing(id)` (a private status helper, not in the public API), then dispatch to the matching `apiRepository.custom.*` method.
4. On 2xx → `markActionSynced(id)`.
5. On 4xx (non-retriable) → `markActionFailed(id, { code, ... })`.
6. On 5xx or network error → leave status at `pending`; the next trigger retries.
7. After flushing, call `clearSyncedActions()`.

That worker is not part of this task. The queue API is.

As of 2026-09-19, the worker scaffold ships at [src/services/syncWorker.js](../src/services/syncWorker.js) with no-network demo handlers and a pluggable registry. The mobile drawer ([src/main.jsx](../src/main.jsx) `MobileMenuContents`) wires a "Sync pending actions" button that calls `syncQueuedActions({ trigger: 'manual' })`. Auto-sync on `online` / `visibilitychange` is exported (`startAutoSync`) but intentionally **not** called — that wiring is a separate task. Full design, handler contract, retry policy, conflict handling, and photo re-pick plan: [docs/SYNC_WORKER_PLAN.md](SYNC_WORKER_PLAN.md). Manual + automated tests: [docs/SYNC_WORKER_TESTS.md](SYNC_WORKER_TESTS.md).

## 8. Future: match actions

The Lead ↔ Listing matching module ([docs/LEAD_LISTING_MATCHING.md](./LEAD_LISTING_MATCHING.md)) is **read-only while offline** in this phase. Match records are surfaced in the lead drawer, the listing drawer, and the mobile lead sheet, but no new match rows can be created, updated, or deleted while the queue is disconnected.

Why deferred: the matching score is computed from live lead + listing state, so creating a match offline risks a stale score when the sync lands and either side has changed. Until the backend `POST /api/v1/leads/:id/match-suggestions` endpoint ships and the queue handlers are written, the offline path is intentionally a no-op for matches.

When this lands, expect three new action types:

- `match.create` — `{ leadId, listingId, matchStatus }` → `POST /api/v1/leads/:leadId/matches`
- `match.updateStatus` — `{ matchId, matchStatus }` → `PATCH /api/v1/matches/:matchId`
- `match.delete` — `{ matchId }` → `DELETE /api/v1/matches/:matchId`

A scheduled visit from a match is already covered by the existing `visit.update` flow (the `listingId` rides through the visit payload) — see [docs/LEAD_LISTING_MATCHING.md](./LEAD_LISTING_MATCHING.md) §6.
